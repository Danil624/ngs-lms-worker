# DECISIONS.md

## Назначение

Этот файл содержит только актуальные решения по проекту.

При конфликте с более старой документацией или историей использовать этот файл как основной ориентир, кроме случаев, когда фактический код требует отдельного анализа.

---

# D-001. LMS становится коммерческим продуктом

Статус: принято.

Система должна развиваться не как решение только для одной компании, а как универсальный коммерческий продукт.

Цель:
- возможность внедрять другим клиентам;
- единая кодовая база;
- минимизация клиентского hardcode;
- возможность продавать доступ без передачи исходного кода.

---

# D-002. Исходный код клиентам не передаётся

Статус: принято.

Предпочтительная модель:
- SaaS;
- лицензия на использование;
- централизованное развёртывание;
- приватный GitHub;
- исходный код контролируется разработчиком продукта.

Клиенту предоставляется доступ к функционалу, но не к репозиторию.

---

# D-003. Ядро LMS отделяется от Bitrix24

Статус: принято.

Bitrix24 рассматривается как интеграционный слой.

LMS Core не должен напрямую зависеть от:
- Bitrix24 domain;
- REST endpoint;
- Bitrix user ID как единственного идентификатора;
- конкретной структуры подразделений клиента.

Нужно постепенно двигаться к отдельным сервисам/адаптерам Bitrix24.

---

# D-004. Не ломать существующую интеграцию при рефакторинге

Статус: принято.

Изменения архитектуры должны выполняться постепенно.

Запрещено полностью переписывать рабочий Bitrix24 flow без необходимости.

Перед рефакторингом:
- изучить текущий сценарий;
- добавить проверки;
- сохранить обратную совместимость.

---

# D-005. Относительные маршруты внутри iframe сохраняются

Статус: принято.

В местах, работающих внутри Bitrix24 iframe, используются относительные URL:

`route(..., false)`

Причина:
ранее абсолютные URL приводили к проблемам:
- 403;
- 419;
- потеря сессии;
- некорректный домен.

Не заменять их обратно без тестирования внутри Bitrix24.

---

# D-006. Мобильная разработка исключена из первого этапа

Статус: принято.

В первый этап НЕ входят:
- отдельная мобильная версия как самостоятельный проект;
- native iOS;
- native Android;
- отдельная мобильная разработка.

Если адаптивность текущего web-интерфейса появляется естественно в ходе frontend-разработки, это не должно превращаться в отдельный scope первого этапа.

---

# D-007. Первый этап определяется STAGE_1_TZ.md

Статус: принято.

Актуальный функциональный scope первого этапа описан в:
`docs/STAGE_1_TZ.md`

Нельзя самостоятельно добавлять:
- геймификацию;
- ИПР;
- 360;
- прокторинг;
- КЭДО;
- вебинары;
- DRM;
- mobile app.

---

# D-008. Клиентский hardcode запрещён в универсальном ядре

Статус: принято.

Не добавлять в LMS Core:
- название конкретной компании;
- домен конкретного клиента;
- ID конкретных сотрудников;
- ID подразделений;
- webhook URL клиента;
- специфичные клиентские поля.

Если требуется уникальная логика клиента, она должна быть изолирована.

---

# D-009. На раннем этапе допустима отдельная БД на клиента

Статус: принято как допустимый переходный вариант.

Не требуется сразу строить сложный shared-database multi-tenancy.

Для первых клиентов допустимо:
- единая кодовая база;
- отдельное развёртывание или отдельная БД на клиента.

При росте продукта можно перейти к более сложной multi-tenant архитектуре.

---

# D-010. Роли должны защищаться на сервере

Статус: принято.

Недостаточно скрывать кнопку HR-панели.

Маршруты HR/admin должны иметь серверную авторизацию/authorization middleware или equivalent Laravel policy/gate.

Codex должен учитывать это при аудите.

---

# D-011. Временные dev-fallback должны быть найдены и оценены

Статус: принято.

В проекте ранее использовался fallback тестового пользователя, если отсутствует `lms_user_id`.

Codex должен:
- проверить, существует ли он в актуальном коде;
- определить, нужен ли он;
- не удалять автоматически;
- предложить безопасный вариант для production.

---

# D-012. Секреты никогда не коммитятся

Статус: принято.

Запрещено добавлять:
- `.env`;
- AUTH_ID;
- access token;
- refresh token;
- webhook secrets;
- API keys;
- production credentials.

Для Codex Cloud использовать отдельные тестовые secrets/environment variables.

---

# D-013. Git-операции требуют разрешения пользователя

Статус: принято.

Codex не должен без явного запроса:
- делать commit;
- push;
- merge;
- rebase;
- создавать PR.

Сначала:
- выполнить задачу;
- показать diff/список файлов;
- сообщить проверки;
- дождаться разрешения.

---

# D-014. Коммиты на русском языке

Статус: принято.

Если пользователь разрешил commit, сообщение должно быть на русском языке.

---

# D-015. Новые зависимости добавлять только при необходимости

Статус: принято.

Не использовать `composer require`, `npm install <package>` и другие новые зависимости без:
- явной технической причины;
- объяснения пользователю.

Предпочитать возможности Laravel и уже установленных библиотек.

---

# D-016. БД изменяется только миграциями

Статус: принято.

Все изменения схемы:
- новые таблицы;
- поля;
- индексы;
- ограничения

делать через Laravel migrations.

Не давать ручные SQL-изменения как основной способ развития проекта.

---

# D-017. Перед изменением сначала аудит существующей реализации

Статус: принято.

Codex должен:
1. найти связанные маршруты;
2. контроллеры;
3. модели;
4. Blade;
5. миграции;
6. существующие тесты.

Только после этого вносить изменения.

---

# D-018. Минимальный diff предпочтительнее переписывания

Статус: принято.

Не переписывать большие рабочие файлы без необходимости.

Предпочитать:
- небольшие изменения;
- отдельные сервисы;
- постепенный рефакторинг;
- сохранение поведения.

---

# D-019. Первый технический приоритет — аудит и отделение интеграции

Статус: принято.

До большого расширения функционала желательно:
1. провести аудит BitrixController;
2. найти hardcode;
3. выделить REST client;
4. выделить auth service;
5. выделить user sync service;
6. определить интерфейс взаимодействия LMS Core с Bitrix24.

Но рефакторинг не должен блокировать реализацию функционала первого этапа.

---

# D-020. Фактический код важнее предположений

Статус: принято.

Документы описывают проект, но Codex обязан проверять фактический код.

Если документация говорит «реализовано», а код не подтверждает это:
- не считать функцию готовой;
- указать несоответствие.

---

# D-021. Первый запуск Codex — без изменений

Статус: принято.

Первое задание Codex Cloud:
- изучить проект;
- провести аудит;
- сравнить с ТЗ;
- определить недостающее;
- найти hardcode;
- определить технический долг.

Первый аудит должен выполняться без изменения файлов.

---

# D-022. Коммерческая оценка не является техническим scope

Статус: принято.

Ранее первый этап оценивался примерно:
- 400–425 часов;
- 1200 ₽/час;
- 8–11 недель при загрузке 40–50 часов/нед.

Эти значения нужны для планирования и КП.

Codex не должен использовать их как основание для изменения архитектуры или сокращения функционала.

---

# D-023. Внешние LMS не являются основой текущего проекта

Статус: принято.

iSpring, IT-Solution и другие продукты рассматривались как альтернативы.

Текущий репозиторий остаётся собственной LMS.

Не копировать архитектуру сторонних решений без отдельной задачи.

---

# D-024. Данные клиента отделяются от продукта

Статус: принято.

Клиентские данные:
- пользователи;
- результаты;
- материалы;
- документы;
- фирменные assets.

Продукт:
- исходный код;
- ядро;
- универсальные сервисы;
- интеграции;
- инфраструктурная логика.

Это разделение должно учитываться при проектировании multi-tenant / export / backup.
