# PRODUCT_ARCHITECTURE.md

## Цель

Превратить текущий проект в универсальный коммерческий LMS-продукт.

Клиент покупает право использования/подписку, но не получает исходный код.

## Целевая модель

```text
LMS Product
├── LMS Core
├── Integrations
│   └── Bitrix24
├── Tenant / Company Configuration
└── Customer-specific modules
```

## LMS Core

Ядро не должно зависеть от конкретного клиента.

В ядро входят:
- курсы;
- уроки;
- треки;
- назначения;
- тестирование;
- попытки;
- домашние задания;
- сертификаты;
- уведомления;
- аналитика;
- роли;
- AI-инструменты.

Запрещено хардкодить в Core:
- домен конкретного Bitrix24;
- ID сотрудников;
- ID подразделений;
- название компании;
- клиентские поля;
- клиентские webhook URL.

## Bitrix24 Integration

Bitrix24 — отдельный адаптер/модуль.

Он отвечает за:
- OAuth/авторизацию;
- получение пользователя;
- синхронизацию сотрудников;
- подразделения;
- REST-запросы;
- webhooks;
- преобразование данных Bitrix24 в внутренние модели LMS.

LMS Core должен работать с внутренними моделями и интерфейсами и не знать детали REST Bitrix24.

## Клиенты / Tenants

В перспективе каждая компания должна иметь собственную конфигурацию:
- название;
- логотип;
- фирменные параметры;
- Bitrix24 domain;
- тариф;
- включённые функции;
- правила уведомлений.

На первом этапе допустима отдельная БД на клиента при общем коде приложения.

Позже возможен полноценный multi-tenant.

## Данные клиента

Клиенту принадлежат:
- пользователи;
- учебные материалы;
- результаты;
- документы;
- фирменные материалы.

Разработчику продукта принадлежат:
- исходный код LMS;
- ядро;
- универсальные модули;
- Bitrix24-коннектор;
- универсальные технические улучшения.

## Специфичные доработки

Специфичная бизнес-логика клиента должна быть отделена от общего ядра.

Пример:

```text
CustomerModules/
└── ClientName/
    └── CustomWorkflow.php
```

Если в процессе создаётся универсальный сервис, он должен оставаться частью продукта.

## Развёртывание

Предпочтительная модель:
- исходный код хранится в приватном GitHub;
- приложение разворачивается на инфраструктуре, контролируемой разработчиком продукта;
- клиент получает доступ к сервису, но не к репозиторию;
- обновления распространяются централизованно.

## Ближайшая архитектурная задача

Перед крупной новой разработкой:
1. провести аудит текущего `BitrixController`;
2. вынести REST-клиент Bitrix24;
3. вынести авторизацию;
4. вынести синхронизацию пользователей;
5. найти клиентские хардкоды;
6. определить сервисные границы LMS Core;
7. не ломать существующую рабочую интеграцию.
