# 1. Общая цель проекта

Проект — корпоративная LMS на Laravel с интеграцией Bitrix24.

Первоначально LMS разрабатывалась как внутренняя система обучения для конкретной компании.

Позже принято продуктовое решение:
система должна развиваться как универсальный коммерческий продукт, который можно внедрять другим компаниям без передачи исходного кода.

Целевая модель:
- закрытый исходный код;
- SaaS / лицензирование;
- единое универсальное ядро;
- отдельный интеграционный слой Bitrix24;
- конфигурация конкретного клиента отдельно от ядра.

# 4. Bitrix24

## 4.1 Авторизация

Реализована реальная авторизация пользователя через Bitrix24.

Контроллер получает:
- `DOMAIN`;
- `AUTH_ID`.

Далее вызывается:
`user.current`.

Пользователь создаётся или обновляется в локальной БД.

Сохраняются:
- Bitrix user ID;
- имя;
- фамилия;
- email;
- должность;
- подразделение.

В сессию сохраняются данные для дальнейшей работы LMS.

---

## 4.2 Синхронизация сотрудников

Была реализована синхронизация через Bitrix24 REST `user.get`.

Использовалась постраничная загрузка пользователей.

Ранее успешно было синхронизировано около 335 сотрудников.

Синхронизация:
- связывает пользователя по Bitrix ID;
- при необходимости ищет по email;
- создаёт новых сотрудников;
- обновляет существующих;
- не должна затирать назначенные вручную роли.

# 6. Проблемы Bitrix24 iframe и маршрутов

При работе LMS внутри iframe Bitrix24 возникали:
- 403;
- 419;
- потеря сессии;
- проблемы с абсолютными URL.

Для исправления в Blade и контроллерах стали использовать относительные URL:

`route(..., false)`

Например:
- возврат к курсу;
- открытие урока;
- завершение урока;
- переход к тесту;
- отправка теста.

Это решение нельзя убирать без проверки поведения внутри iframe.

# 8. Публичный доступ во время разработки

Использовались два подхода:

## 8.1 Cloudflare Worker

Cloudflare Worker использовался как публичная точка доступа.

Возникли проблемы:
- браузер мог не открывать приложение;
- iframe Bitrix24 работал нестабильно;
- `curl` мог возвращать 200, хотя браузер не работал;
- были подозрения на QUIC / HTTP3 и особенности корпоративной сети.

В итоге Worker перестал считаться основным вариантом.

## 8.2 Tailscale Funnel

Tailscale Funnel оказался стабильнее.

Он проксировал внешний HTTPS-адрес на локальный Laragon.

Была проблема, когда другое приложение переключало Funnel на другой локальный порт.
Поэтому при неожиданных страницах нужно было проверять `tailscale funnel status`.

Эти адреса относятся только к окружению разработки и не должны быть частью ядра продукта.

# 9. EmployeeLessonController

Контроллер:

Если авторизация Bitrix24 полностью рабочая, такой fallback желательно убрать или ограничить dev-окружением.

# 12. Решение по продуктовой архитектуре

Принято:
LMS не должна оставаться приложением только под одну компанию.

Нужно постепенно разделять:

```text
LMS Product
├── LMS Core
├── Integrations
│   └── Bitrix24
├── Tenant / Company Configuration
└── Customer-specific modules
```

В ядро должны входить:
- курсы;
- уроки;
- треки;
- назначения;
- тестирование;
- домашние задания;
- сертификаты;
- уведомления;
- аналитика;
- роли;
- AI.

Bitrix24 должен быть адаптером.

Не должно быть hardcode:
- домена компании;
- ID пользователей;
- ID подразделений;
- конкретных названий клиентов;
- webhook URL;
- клиентских секретов.

# 13. Multi-tenant направление

Обсуждались два подхода.

## Вариант на раннем этапе

Один код приложения + отдельная БД каждому клиенту.

Плюсы:
- проще изоляция данных;
- проще резервные копии;
- проще удаление/экспорт клиента;
- ниже риск случайной утечки между tenants.

## В перспективе

Полноценная multi-tenant архитектура.

Но переход к ней не должен мешать завершению первого этапа.

# 14. Модель коммерциализации

Цель владельца продукта:
- продавать доступ к LMS;
- не передавать исходный код;
- сохранять право использовать платформу у других клиентов.

Предпочтительная модель:
- SaaS;
- бессрочная или срочная лицензия на использование;
- исходники остаются у разработчика;
- клиент владеет своими данными и контентом.

Клиенту принадлежат:
- сотрудники;
- результаты обучения;
- учебные материалы;
- внутренние документы;
- логотип/фирменные материалы.

Разработчику принадлежат:
- исходный код;
- ядро;
- универсальные модули;
- Bitrix24-коннектор;
- универсальные технические улучшения.

Юридические формулировки требуют отдельной проверки юристом.

# 16. Оценка первого этапа

Исторически первый этап оценивался примерно в:
- около 400–425 часов после исключения мобильной части;
- ставка обсуждалась 1200 ₽/час;
- ориентировочный срок при загрузке 40–50 часов в неделю — около 8–11 недель.

Эти цифры являются коммерческой оценкой, а не техническим ограничением.

Codex не должен менять scope или сроки самостоятельно.
